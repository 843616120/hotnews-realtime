# 01 项目架构与数据字典

## 概念说明

实时链路从 Kafka 持续读取文章与行为，按业务事件时间处理乱序。`article_id` 用于关联，`event_id` 用于行为去重；窗口结果与原始事件不是一对一关系。MySQL 保存可追溯明细、告警和历史榜单，Redis 只保存最新榜单。数据字典区分生成器的严格 JSON Schema 与 Flink 实际 ETL：运行时由 `ArticleJoinBehavior.validate` 按必填字段、时间和业务值校验，并未调用 JSON Schema 校验器执行全部约束。

## 项目中的具体实现

```text
生成器 (JSONL + 可选 Kafka)
       | topic_article (3 分区)     topic_behavior (6 分区)
       +-------------+--------------------+
                     v                    v
              KafkaSource -> JSON ETL / dirty_data -> MySQL
                     |            |
                     |      event_id 去重 (24h TTL)
                     +-------+----+
                             v
              文章/行为 event_time Watermark (30s 乱序, 30s 空闲)
                             v
               article_id Join / 行为先到暂存并补关联
                   | late_data / unmatched_behavior -> MySQL
                   v
           恢复行为时间戳, 保留上游 Watermark
                   v
           clean_behavior 去重 -> MySQL clean_behavior
                   |
          +--------+---------+----------+
          v                  v          v
    A 5min 滑动窗     B 10min 滚动窗   C IP 1min 回看状态
    click > 1000     click/share/      >50 不同文章且
    -> article_alert  comment Top5     平均阅读 <2000ms
                      -> category_rank -> ip_alert
                      -> Redis 最新榜单
    规则超期旁路 -> MySQL pipeline_event
```

入口和模块：`flink-common` 放 Kafka/JDBC/Redis/Watermark/Checkpoint 工具，`flink-join` 放 `ArticleJoinBehavior`，`flink-rules` 放 `Achieve_roleA/B/C/All`。独立 A/B/C 各自创建 Join；统一入口只建一次 Join，三个规则共用清洗流。统一入口将文章复制为 8 个盐副本、行为按 `event_id` 选盐以分散热点 Join key；行为仍只关联一次。统一作业并行度 3，B 的 `windowAll` 及榜单 Sink 并行度 1；Compose 当前为 1 个 TaskManager、8 slots，`parallelism.default: 2` 被入口的 3 覆盖。单机、单副本 Kafka (`replication-factor=1`) 是考核环境，不是高可用集群。

| Topic | 分区 / 副本 | 数据与起点 | 设计依据 |
| --- | --- | --- | --- |
| `topic_article` | 3 / 1 | 文章发布/更新；每次从 earliest 构建文章状态 | 和 3 个 Source/Join 子任务对齐；文章版本取较新者 |
| `topic_behavior` | 6 / 1 | 点击/分享/评论；消费组已提交位点优先，无位点从 earliest | 分区数高于并行度 3，实际负载仍可能集中在热点分区；Checkpoint 提交位点 |

### 输入数据字典

两流的时间字符串是带时区的 ISO-8601，运行时经 `OffsetDateTime` 解析为完整 epoch 毫秒。`ingest_time` 只用于模拟到达次序和“事件时间不可比到达时间超前 2 小时”的校验，不用来生成 Watermark。生成器的 schema 定义见 `generator/schemas/`。

| 流 | 字段 | 类型 / 作用 |
| --- | --- | --- |
| article | `event_id`, `article_id` | 字符串；文章事件 ID、Join key |
| article | `event_type`, `version` | `publish/update`；正整数版本，更新保留较新版本 |
| article | `title`, `category`, `tags` | 标题、分类、非空标签数组；Join 富化行为和 B 分类榜单 |
| article | `published_at`, `event_time`, `ingest_time` | 发布时间、事件时间、模拟到达时间 |
| behavior | `event_id`, `user_id`, `article_id` | 字符串；去重键、用户 ID、Join key |
| behavior | `action`, `ip`, `read_duration_ms` | `click/share/comment`；IP 为 C 的 key；时长毫秒 0~86400000 |
| behavior | `event_time`, `ingest_time` | 行为事件时间（A/B/C 窗口及 Watermark）、模拟到达时间 |
| joined / clean | 输入行为字段 + `title`, `category`, `tags`, `article_published_at`, `article_version` | Join 富化；进入规则前再按 `event_id` 去重 |

### 查询与主键

| MySQL 表 / Redis Key | 唯一键或结构 | 用途 |
| --- | --- | --- |
| `clean_behavior` | `event_id` | 清洗后的富化明细，UPSERT |
| `dirty_data` | `(source_stream, record_id)` | JSON/字段/时间解析失败的原文 |
| `late_data` | `(source_stream, event_id)` | 超过 Join 65min 阈值的留痕；Join 仍尝试关联 |
| `unmatched_behavior` | `event_id`, `matched` | 行为先到暂存、文章到达补关联、超时待回放 |
| `article_alert` | `(window_start_ms, article_id)` | A：5min 窗/1min 滑步，点击严格大于 1000 |
| `category_rank` | `(window_start_ms, rank_no)` | B：10min 滚动窗，各分类行为总数 Top5，含 `top_articles` 与 `revision` |
| `ip_alert` | `(alert_minute_ms, ip)` | C：同 IP 1min 回看，超过 50 篇不同文章且平均阅读严格小于 2000ms；支持修订/撤销 |
| `pipeline_event` | `(event_type, event_id)` | A/B/C 超出在线补算范围的审计事件 |
| `hotnews:top5:latest` | Redis Hash: `window_start_ms`, `window_end`, `revision`, `ranking` | 最新窗口完整 JSON 榜单；成功更新续期 7200 秒，旧窗口/较旧修订被 Lua 拒绝 |

建表定义以 `sql/01-hotnews-tables.sql` 至 `05-rule-c-ip-alert.sql` 为准。A/B 窗口允许迟到 65min，C 在线状态保留补算 65min；超过范围写审计，不自动回填历史窗口。文章状态 TTL 2h，行为 `event_id` 去重 TTL 24h，IP 状态详见 `03-状态TTL与内存模型笔记.md`。

## 测试结果

`generator/generator/total_data/generation_report.json` 固定批次记录 500 篇文章、100000 条行为、998 条注入脏数据和 4000 条注入重复记录；两个热点文章占点击的 84.8325%。独立规则/边界核对与 MySQL/Redis 最新榜单一致性的通过范围见 `tests/roles/summary/reports/rule-ab-acceptance-20261007.md`。统一作业 RocksDB 样本中 A/C 与 SQL 一致，B 为 SQL 64 行、Flink/MySQL 55 行，缺最后两个窗口共 9 行，见 `tests/roles/state-backend/reports/role-all-result-check-20261008-rocksdb.md`。Day6 batch=200 的 5000/s 目标档最终读完 100000 条，18 次 Checkpoint 成功；Source 区间实测约 79~167/s，见 `tests/roles/performance/reports/day6-5000-batch200-20261008.md`。

## 问题和结论

分区数和算子并行度不同：六个行为分区在三个 Reader 上不平均，热点文章和 B 的单并行度窗口仍可引起反压。按业务唯一键 UPSERT 能约束重放写入，但不能把固定批次读完或独立规则通过表述成统一作业全量一致/持续 2000/s 已通过；必须按同一批输入、窗口和最终版本核对。架构图与数据字典描述的是当前代码和已留存的测试现场，而非计划中的理想拓扑。
