时间：2026-10-06（Asia/Shanghai）。按《鲍献锐-Flink 大数据 7 天学习目标与考核标准》
第 6 天验收。运行环境：Docker Flink 1.17.0 / Kafka Compose，单 TaskManager
实际 4 个物理 CPU、8 个 Task Slot、2 GiB 进程内存。压测入口是从
`Achieve_roleA` **独立复制**的 `Day6BackpressureJob`；源程序保持原样。
模拟 Sink 不写真实 MySQL/Redis；Kafka 压测使用独立 `hotnews-day6-*` Topic，
1 小时保留期，绝不复用业务消费组。所有结果仅代表这台本机及此负载。

**定位**：Sink 同步等待占用任务线程，输出缓冲填满后 Source 的
`backPressuredTimeMsPerSecond` 升高；数据仍在规则流经过，完成时间从
28.343s（并行 4）增至 54.667s（并行 2），不是规则 A 计算错误。
增大 Sink 并行度后，同批次总耗时缩短约 **48.2%**、含启动吞吐由
约 **915/s 提高到 1,764/s（1.93 倍）**；这是模拟延迟下的结果，
真实数据库并行增大可能反而使连接数/锁竞争恶化，需另测真实存储。
减小 Source 并行度只会压低消费速度，使 Kafka Lag 增大；外部
持续进入的总流量并没有降低，不能解决 Sink 总容量不足。

## Kafka Lag、延迟与追平

Kafka 正常档也使用独立 Topic `hotnews-day6-fast5000-muwa7jzm`：
生产器发送 100,000 条，实测 4,999.0 条/s；Job
`ad3605338e6b345aa045da417b351828` 的最终 Source/规则/Sink
各收到 100,000 条、成功 Checkpoint 8 次，最终三分区 Lag 均为 0。
采样期间 Lag 短时最高 22,244，随后已追平；运行器在采样后
**主动取消专用常驻作业**，不是故障退出。证据见以
`kafka-fast5000-` 开头的两份结果文件。此处生产器发速是实测，
并不能据瞬时 Lag 峰值声称稳定 Sink 容量低于 5,000/s。

隔离 Topic `hotnews-day6-slow-muw95ftn`，生产器发送 40,000 条 200 字节
记录，实测 1,999.6 条/s；慢 Sink 2ms、并行 2。Job
`c2b5b487198083bfbbd136d8b8452396` 的消费组 Lag 在采样中
从 16,399 上升到 **25,583**，生产结束后下降，取消前为 **10,988**；
Kafka 最终分区 Lag 为 4,995 / 0 / 5,993。同步 Sink 期间最近一条消息
到 Sink 的延迟最高 **17,320ms**（单条观测，不是 p95），
Checkpoint 用时约 **2.7s**，正常合成档运行中约 15-20ms；
跨 Kafka/合成 Source 不能把差值全部归因于 Barrier 对齐。
生产工具分区不均也限制恢复速度，不把它误判为纯 Sink 问题。

同 Topic/消费组从**已提交位点**恢复，Sink 并行度改为 4；
`d7af57a48f6bfd86751077c59f329db5` 追平作业记录
Lag 8,615 → 6,247 → 0 → 0，已有 4 个成功 Checkpoint；
从恢复提交到连续两次确认为零用时 **20.249s**（含启动和位点提交等待）。
原始证据：`kafka-slow-2026-10-06T05-43-43.163Z.json`、
`kafka-slow-muw95ftn-run.json`、`kafka-recovery-1791265819322.json`。
第二轮独立复测 `hotnews-day6-audit-muwa1vfv` 同样发送 40,000 条，
取消前 Lag 为 11,242；恢复文件 `kafka-recovery-1791267061630.json`
逐次保存 Kafka 原始分区位点及 Checkpoint：
**8,870 → 8,308 → 8,308 → 8,168 → 0 → 0**，用时 21.342s。
对应原始运行文件为 `kafka-audit-muwa1vfv-run.json` 和以
`kafka-audit-2026-10-06T06-09-03.561Z` 开头的采样 JSON。
这不是业务表恢复核对，也不证明真实 MySQL/Redis 端到端 Exactly-Once。

容量公式（事件单位）：

- 若输入 2,000/s、受压处理 1,000/s，积压增长约
  `2,000 - 1,000 = 1,000/s`；持续 1 小时约 **360 万条**，
  单按 200 字节 payload 约 **720 MB**，尚未计 Kafka 索引、副本、
  协议及分区开销。实际 Lag 是已提交 offset 的差，5 秒 Checkpoint
  使其台阶式变化，不能从单个点反推精准处理速率。
- 以取消前 10,988 条为例，若停止写入、有效恢复容量 2,000/s，
  理想下限约 `10,988 / 2,000 = 5.5s`；实际连同部署、
  分区不均和提交确认用了 20.249s。若生产持续 2,000/s，
  恢复容量恰为 2,000/s，则净追平能力为 0，永远追不上；
  需要 `追平秒数 = 当前 Lag / (稳定消费速率 - 新增速率)` 且分母 > 0。
- Kafka 隔离 Topic 配置 `retention.ms=3,600,000`；
  20 秒实验消费有足够余量，但**不能**把 1 小时保留当成业务 Topic
  的当前配置。生产保留期须大于最长故障 + 排队追平 + 运维缓冲。

## 内存、状态与故障鉴别

TaskManager REST 返回进程总内存 2,147,483,648 B，JVM 堆最大
698,351,616 B（约 666 MiB），Task Heap 563,714,445 B，
网络内存 166,429,984 B（约 159 MiB），托管内存 665,719,939 B
（约 635 MiB）；G1 Young/Old GC 由每轮快照记录。慢 Sink 截图
对应作业样本中网络缓冲最多占 228/5,079 个分段（约 7.1 MiB），
没有网络缓冲耗尽的证据；状态增长档的堆观测峰值约 410.5 MiB，
基线约 332.6 MiB，GC 累计时间分别增加约 84ms 与 22ms。
共享 JVM 会受其他活动与 GC 时点影响，不能把堆差全部归因于键数。
本次没有实测 OOM。

运行中的 Checkpoint 状态：200 键基线约 148,264 B，
10,000 键实验约 5,858,664 B（约 **39.5 倍**）；对应快照
持续时间约 15ms 与 139ms。粗略线性外推 100,000 键可能有
约 59 MB 快照，**仅为风险估算**；加上对象/哈希表开销和同机
多个作业，很可能先出现 GC/Checkpoint 超时，再到 OOM。
规则 A 每篇文章最多五个滑窗且关窗后保留 24 小时，
键数、乱序修正和定时器都影响实际状态大小。RocksDB 使用
托管内存/本地磁盘、HeapStateBackend 使用 JVM 堆；当前压测
未进行 RocksDB 对照，不能声称其更快或已消除风险。

排障顺序：Sink Busy 高、Source Backpressured 高且 Lag 增长，
优先查慢写入/连接池/并行度；若状态与快照体积持续增长而
Sink 不忙，查 TTL、热键与定时器；若网络缓冲可用量趋近零，
查网络内存/分区；若 GC 时间与暂停增大且堆接近上限，
查对象分配及堆压力。Watermark 不前进须另查空闲分区，
不能简单归入 Sink 反压。

## 工程化与代码审计

- Docker Compose 已外置 `.env`，Kafka/Flink/MySQL/Redis 一键入口为
  `deploy/start-all.ps1`，参数与恢复步骤在 `deploy/README.md`；
  Day 6 可复现脚本及指标定义在 `tests/day6/README.md`。
  不读取或提交现有凭据、不覆盖业务输出。
- Flink 运行镜像 `flink:1.17.0-scala_2.12-java11`，Maven Flink
  1.17.0、Kafka Connector 1.17.0；Kafka 客户端随 JAR 解析为
  3.2.3，Compose Broker 镜像为 `cp-kafka:7.5.0`。
  作业从同组**已提交 Kafka 位点**重启，不用规则 A 原作业的
  Savepoint；换了 Source/拓扑、状态描述符和 Sink 并行度后
  不能直接宣称与旧 Savepoint 状态兼容。升级应先核对连接器、
  序列化器/UID、状态后端与目标镜像，再在隔离环境恢复验证。
- 代码审计风险 1：原规则 A 的 `CountClicks.onTimer` 遍历该键
  全部窗口，24 小时保留与热键修正会放大状态和定时器数量；
  建议用有上界的状态监控及热点键回归，不在本次改动原文件。
- 风险 2：`Day5MySqlSink` 在 `invoke` 或 Checkpoint 前同步批量
  提交；MySQL 抖动将拖慢 Barrier 并把压力传到 Source。
  后续需测真实批量大小、数据库连接上限、重试和连接耗尽，
  避免只靠加并行度治标。
- 风险 3：`Day5RedisRankSink` 为单并行度同步 Lua 写入；
  Redis 延迟或故障使榜单链路受阻，且 Key TTL 过期后失去
  版本比较记忆；应监控耗时/重试、TTL 与重放覆盖边界。

对**本次 AI 生成的 Day 6 代码**另做自审，避免把压测器本身当作真值：

1. 合成 Source 以 `Instant.now()` 打事件时间，模拟 Sink 仅 `sleep`，
   不能据此推断 Kafka Lag 或真实数据库吞吐。处理：另增隔离 Kafka
   模式并在指标文件中分开命名，真实 MySQL/Redis 仍标为未验证。
2. Kafka 模式用 `ConsumerRecord.timestamp()` 计算延迟；若 Broker
   改用追加时间或生产端时间戳失真，端到端数值会偏差。处理：
   留存原始时间戳/位点，生产环境须核对 Topic 时间戳策略，
   不把 `day6_last_latency_ms` 宣称为 p95。
3. 高键数实验每条消息会格式化文章 ID，窗口算子为每条点击
   更新五个状态项；极端输入可能首先耗尽 CPU/堆并污染 Sink
   吞吐结论。处理：固定 200/10,000 键对照、记录各算子指标与
   Checkpoint 体积，禁止外推到未实测的负载规模。

**未验证**：真实 MySQL/Redis 写入降速对吞吐的影响、真实业务
Topic 的保留期与 Lag、RocksDB 对照、实际 OOM、生产业务结果
在故障恢复后的逐键一致性。模拟数据不能替代这些结果。
