## 概念说明

Key 倾斜指少数 key 占用过多计算/状态。同一 `article_id` 在 `keyBy` 后必须由同一 Join Subtask 处理；增加并行度不能拆开单个热点 key。Web UI 的 busy、backpressured 和 idle 要按 **Subtask** 比较，算子上的 max 值不能直接代表所有 Subtask。Checkpoint 对齐和 JDBC 提交也可能受到下游堵塞影响。

## 项目中的具体实现

- `total_data/generation_report.json` 给出 100,000 条行为、82,306 次点击，两个热点文章占全部点击约 84.8325%，折合约 69,820 次点击。Topic `topic_article` 实测 3 个分区、`topic_behavior` 实测 6 个分区；IDEA 统一作业并行度 3，原 Join 的 `keyBy(article_id)` 也是 3，规则 B 的 `windowAll` 固定并行度 1。行为 Kafka 分区按文章 ID 写入，源端本身也可能倾斜；增加 Join 盐并不会改写 Kafka 分区数据。
- **本次已运行的优化**：统一作业 `Achieve_roleAll` 将 Join 配置成 8 个盐；行为按稳定的 `event_id.hashCode()` 分配一个盐，文章对 8 个盐复制，再按 `article_id#salt` 分区。每个行为只进一个分片、只 Join 一次，输出前移除内部盐字段；`event_time`、乱序/空闲 Watermark 与三个规则不变。单独 A/B/C 入口仍用原来的无盐 Join。500 篇文章至多约 4000 个加盐文章 key（不计文章版本/反复重放），增加文章分发量及约 8 倍文章状态副本，换取热点行为分散到多个 Join Subtask；这不是对 Kafka 原始 key 分区的加盐。
- 优化版默认消费组前缀 `hotnews-role-all-salted`，不同于基线的 `hotnews-role-all`，避免只从旧版的提交位点读取尾部。重复整批实验可设置 IDEA 环境变量 `HOTNEWS_ROLE_ALL_GROUP` 为新的唯一前缀；新组行为流无位点时从 earliest 开始。优化版的 Topic 已核对为 500 篇文章、约 100,000 条行为的位点规模；**基线的起始位点未留存**，不能仅凭总量宣称严格同位点前后吞吐可比。重跑期间旧作业必须停止，避免共同 UPSERT 污染结果。
- 优化前**只加测量代码**：Join 每个 Subtask 暴露 `join.behavior_input`、`join.article_input`、`join.pending_input`、`join.direct_matches`、`join.rejoined_matches` 和 `join.etl_to_output_p95_ms`；后者是最近 2048 条已匹配行为从 ETL 验证后到 Join 输出的实际处理时钟延迟，包括排队和等待文章，不包括 Kafka 写入到 Source 读取的时间，也不代表规则窗口完成或 MySQL 写入的延迟。内部测量字段在输出前删除，不进入业务表或规则数据。
- Kafka Lag 用消费组按分区的 `LOG-END-OFFSET - CURRENT-OFFSET`，单独记录文章组 `hotnews-role-all-article` 与行为组 `hotnews-role-all-behavior`；已提交位点随 Checkpoint 更新，Checkpoint 失败时它可能滞后于正在读取的实时位点。相同输入批次、起始位点、发送速率和计算资源，才可比较优化前后。

## 问题和结论

- 优化前 Join 输入和 busy 已坐实**运行时不均衡**；加盐后最大 Subtask 累计占比从基线样本的 60%~76% 降至本次样本的约 39%~41%，但前后采样时间、处理阶段、位点尚不严格一致，只能说明**本次加盐确实把热点 Join 流量分散到了三个 Subtask**，不能宣称全链路吞吐提升的严格倍数。算子链包含 JDBC Sink，忙碌不等于纯 CPU 倾斜；B 的 `windowAll` 和 JDBC、Kafka 源热分区仍可能限制总体速度。加盐在 Join 之前，行为只 Join 一次，A/B 不能再次把计数叠加。
- 优化只改善热点 key 的分配，**不保证**旧事件在 Watermark 超过 65 分钟时还能参加 A/B/C。规则结果与离线 SQL 的一致性本轮尚未达到验收条件，等重新跑同批次并解决 late 后再对比；不要将吞吐改善写成结果正确性验证通过。
- 采集期若重启或消费组位点发生变化，记录 Checkpoint/恢复点并重新划定对比区间。当前尚无 OOM 现场证据，不写 OOM 已修复；Join 加盐已完成并采样，B 的两阶段聚合、规则超期补算和结果一致性仍未完成。Web UI 采样数值与 Job ID 已记录，但未归档此轮 Web UI 截图；最终报告的监控截图需另行保存，不把文字记录冒充截图证据。

## 第五天故障前资源采样（2026-10-08）

### 概念说明

busy/反压描述任务线程时间，不等同 CPU 使用率；同链窗口与 JDBC 无法只凭 busy 区分耗时。每子任务滚动 p95 不能相加或平均成全局 p95；Sink 写入次数包含窗口修订，不等同数据库主键行数。

### 项目中的具体实现

Docker RocksDB Job `d933102253fcaaeb92dd34ce2faa8750`，1 TM、8 slots、实际使用 3 slots、42 子任务。`capture-webui.ps1` 保存所有子任务指标，`RecoverySnapshot.java` 只读 MySQL/Redis 和 Kafka Admin 位点。顺序采样保存起止时间，不把不同接口查询视为同时快照。

### 问题

本轮没有稳定外部生产速率或长时间峰值观测，因此无法据此给出可承诺的持续容量；不能跨IDEA/Docker、不同内存预算和处理阶段计算HashMap/RocksDB速度倍率。Kafka已消费完、下游也稳定后才准备Kill，仍需安排有实际重放的故障阶段。大量规则late仍存在，正确性未通过。

### 结论

证据已覆盖吞吐、各子任务p95、分区Lag、CK时长与资源。反压与重复窗口修订有现场证据，但窗口计算和JDBC的各自贡献尚未隔离。容量正式计算需补稳定输入速率、服务速率、峰值内存/状态增长和目标故障恢复时间，不能用空闲CK推导生产容量。
