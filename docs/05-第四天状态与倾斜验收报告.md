# 第四天状态、TTL 与 Key 倾斜验收报告

## 1. 验收范围

本报告对应考核要求：

1. 设计文章热度状态和 IP 状态，明确 TTL、字段、清理依据。
2. 用热点数据制造 Key 倾斜，记录优化前吞吐、p95 和 Subtask 分布。
3. 使用加盐和两阶段聚合优化，并证明优化前后规则结果一致。
4. 对比 Memory/HashMap 与 RocksDB 的资源影响，说明切换大状态后端的条件。
5. 验收重复事件、规则 C 的 49/50/51 篇文章边界，以及 1999/2000 ms 阅读时长边界。

程序和代码说明：

- `ArticleHeatStateJob`：文章热度状态作业；原始模式按文章 Key，`--optimized` 按 16 个事件 ID 分片后两阶段合并。
- `IpWindowStateJob`：IP 状态作业；原始模式按 IP，`--optimized` 按 16 个事件 ID 分片后两阶段合并。
- `RoleStreamUtil`：Join 后二次幂等保护和事件时间恢复。
- `Day4SkewBenchmark`：固定热点输入的本地基准，输出 JSON 证据。

两项独立状态作业复用 ETL、Join 和 Watermark，但不修改规则 A/B/C。IP 状态作业的一分钟不重叠窗口用于考核状态设计；规则 C 仍保持“每次点击回看一分钟”的业务语义。

## 2. 状态设计

| 业务状态 | 记录内容 | Key | TTL/清理 |
| --- | --- | --- | --- |
| 文章窗口局部状态 | 点击数、文章版本、标题、分类、窗口起止、分片号 | `article_id#shard` | 窗口结束 + 30 秒合并并删除局部窗口；最近热点快照 24 小时 TTL。 |
| 文章最近热度 | 最近一次超过 1000 的文章热度结果 | `article_id` | 24 小时处理时间 TTL。 |
| IP 窗口局部状态 | 不同文章集合、点击数、阅读时长总和、窗口起止 | `ip#shard` | 窗口结束 + 30 秒合并；局部、最近窗口、最近告警状态均 1 小时 TTL。 |
| 行为去重状态 | `event_id` 是否已处理 | `event_id` | 24 小时处理时间 TTL，Join 前执行。 |
| 规则 C 告警版本 | IP 点击明细和每分钟告警版本 | `ip` | 按规则 C 的事件时间修正策略处理；不以 Day 4 IP 状态替代。 |

IP 完整窗口输出至少包含：`ip`、`article_ids[]`、`article_count`、`click_count`、`duration_sum`、`avg_read_duration_ms`、`window_start`、`window_end`。集合使用去重文章 ID，平均时长为 `duration_sum / click_count`。

## 3. TTL 与容量依据

### 3.1 文章状态 24 小时

文章热度需要覆盖一个业务日内的迟到修订、重放和最近热度读取，因此最近热度状态保留 24 小时。窗口局部状态并不等待 24 小时才清理，而是在事件时间窗口结束并经过 30 秒允许迟到后由定时器合并和删除。TTL 是停更兜底，不负责关窗。

### 3.2 IP 状态 1 小时

IP 作业是一分钟窗口。1 小时保留 60 个窗口长度，足以覆盖短时间停更、重试和迟到修订；对于持续不活跃 IP，可以较快回收集合状态，避免高基数 IP 无限增长。窗口结束后仍按 Watermark 和 30 秒允许迟到结算。

### 3.3 数量估算

| 假设 | 估算结果 | 说明 |
| --- | ---: | --- |
| 100000 行为/小时、24 小时、80 B/去重状态 | 192 MB | 未包含 JVM 对象、Flink 元数据和 Checkpoint 开销。 |
| 2000 行为/秒、24 小时、80 B/去重状态 | 13.8 GB | 约 1.728 亿条，普通 JVM 堆不可直接承接。 |
| 120000 个不同文章 ID/分钟、80 B/ID | 9.6 MB/窗口 | 还要加 HashSet、序列化、Map 和分片开销。 |

若要修改 TTL，先以生产峰值速率、唯一键比例、允许补算跨度和可用内存重新估算，再用固定批次验证结果。当前 TTL 不修改，清理由窗口定时器、TTL 过期检查和 Checkpoint/后端 compaction 共同完成；TTL 到期不保证物理空间立刻回收。

## 4. 倾斜优化方案

### 4.1 优化前 Key

```text
文章：article_id
IP：  ip
```

本次基准每组 12000 条事件，其中 10800 条，即 90%，集中到一篇文章或一个 IP，并行度为 3。原始 Key 会将热点集中到单个 Subtask。

### 4.2 加盐与两阶段聚合

```text
firstKey = businessKey + "#" + floorMod(hash(event_id), 16)
```

第一阶段分别按 `article_id#shard` 或 `ip#shard` 聚合；第二阶段按原业务 Key 合并。文章计数相加并保留最新文章维度；IP 对文章集合求并集、对点击和阅读时长求和。最终窗口输出条件不变，因此优化不是放松阈值或改变时间语义。

迟到事件仍受 Watermark 和 30 秒允许迟到控制。进入旁路的数据保留 `late` 证据，并继续尝试 Join/补算；加盐只改变状态分布，不改变迟到处理和结果口径。

## 5. 优化前后实测结果

证据文件：`tests/day4/results/local-skew-hashmap-2026-10-06T05-00-09.163Z.json`。

测量定义：吞吐为输入事件数除以本地作业墙钟时间，包含启动和结束开销；p95 为 Source 打点到 keyed 探针，不是完整窗口告警端到端延迟。每种模式交错运行两轮，表中吞吐和 p95 为两轮平均值。

| 场景 | 模式 | 吞吐 events/s | p95 ms | Subtask 0/1/2 |
| --- | --- | ---: | ---: | --- |
| 文章热度 | 优化前 | 6846.22 | 9.79 | 480 / 11160 / 360 |
| 文章热度 | 16 分片加盐 | 6651.98 | 7.23 | 5681 / 2426 / 3893 |
| IP 状态 | 优化前 | 7192.67 | 3.69 | 11520 / 360 / 120 |
| IP 状态 | 16 分片加盐 | 7108.12 | 4.73 | 3796 / 3759 / 4445 |

结论：

- 文章热点从单一 Subtask 的 11160 条变为 5681/2426/3893，IP 热点从 11520/360/120 变为 3796/3759/4445，分布明显改善。
- 本地小样本吞吐没有稳定提升：文章和 IP 均略低于对应基线；这符合加盐增加第二阶段聚合成本的预期，不能只凭吞吐宣布优化成功。
- 本轮探针 p95 文章下降，IP 略升；p95 受本地启动、JVM 和调度噪声影响，不能替代 Docker 集群端到端延迟。

## 6. 结果一致性与边界验收

### 6.1 加盐前后结果

`window_results_equal = true`：

- 文章热度：5 个滑动窗口，热点文章每窗口 `click_count = 10800`，前后文章 ID、分类、标题、窗口起止一致。
- IP 状态：1 个窗口，`click_count = 10800`、`article_count = 80`、`avg_read_duration_ms = 1000`，`article_ids[]` 集合和窗口起止一致。

### 6.2 重复事件

行为 ETL 在 Join 前按 `event_id` 使用 `ValueState` 去重，规则入口继续做二次幂等保护。重复行为不会重复进入文章计数、IP 点击数、阅读时长总和或告警版本。Java 回归用例已验证重复输入只保留一份有效行为。

### 6.3 规则 C 文章数边界

规则 C 条件为不同文章数大于 50，测试结论如下：

| 不同文章数 | 结论 |
| ---: | --- |
| 49 | 不告警 |
| 50 | 不告警 |
| 51 | 告警 |

### 6.4 规则 C 阅读时长边界

规则 C 条件为平均阅读时长小于 2000 ms，测试结论如下：

| 平均阅读时长 | 结论 |
| ---: | --- |
| 1999 ms | 满足时长条件，可告警 |
| 2000 ms | 不满足时长条件，不告警 |

## 7. Docker Linux 资源验收

### 7.1 实验条件和有效性

Docker 集群使用固定批次：500 条文章、100000 条行为、文章 Topic 3 分区、行为 Topic 6 分区、作业并行度 3、TaskManager 8 slots、5 秒 Checkpoint。采集脚本为 `tests/day4/run-docker-day4.ps1`，每组使用唯一消费组。以下 8 个 JSON 均满足 `input_behavior_records=100000`、`valid_full_batch=true`、`had_restart=false`，半批和重启样本未纳入：

| 场景 | 后端/模式 | Job ID | 吞吐 events/s | 时长 s | TM 峰值 MB | RocksDB 峰值 MB | Checkpoint |
| --- | --- | --- | ---: | ---: | ---: | ---: | --- |
| 文章 | HashMap/基线 | `e7e9515525aaabde8c6a78a709992cea` | 10385.29 | 9.63 | 955.9 | 0 | 2/2 |
| 文章 | HashMap/加盐 | `1dcc830f009c47d1a42ac2c4f783d9fb` | 7276.43 | 13.74 | 1060.9 | 0 | 3/3 |
| 文章 | RocksDB/基线 | `f00627384a2c38ddaf7087064ed2815c` | 933.58 | 107.12 | 1173.5 | 4.61 | 7/7 |
| 文章 | RocksDB/加盐 | `f7a3a7996a8a58e7a7dae504c54ff091` | 679.34 | 147.20 | 1226.8 | 5.17 | 6/7，1 失败 |
| IP | HashMap/基线 | `5c81f1382114bafca604e00c84cd8649` | 6478.36 | 15.44 | 1208.3 | 0 | 3/3 |
| IP | HashMap/加盐 | `9cf6125cd2dd308a99466ab6c597caab` | 9659.97 | 10.35 | 1297.4 | 0 | 2/2 |
| IP | RocksDB/基线 | `dbf78dcfd75bad286834a829e4de4bcf` | 1156.35 | 86.48 | 1361.9 | 4.55 | 7/7 |
| IP | RocksDB/加盐 | `733c62bb3647c9183ca025e9f9e662c8` | 1417.78 | 70.53 | 1353.7 | 4.60 | 6/7，1 失败 |

吞吐定义为 `100000 / duration_ms * 1000`，只作同一 Docker 环境下的相对比较。RocksDB 在本批次明显慢于 HashMap，并占用约 4.55～5.17 MB 本地状态目录；这是序列化、JNI、I/O 和 compaction 成本的实测体现。加盐不是“必然提速”：文章 HashMap/RocksDB 均下降，IP 本批次均上升。两组 RocksDB 加盐作业各出现 1 次 Checkpoint 失败，但最终作业状态为 `FINISHED`；这项风险不能省略。

### 7.2 p95 和 Subtask 口径

正式 Docker 作业没有 Source-to-keyed Probe，所以所有 Docker JSON 的 `p95_source_to_keyed_ms` 为 `null`。Checkpoint 时长、busy time、backpressure time 不能替代 p95。优化前后的 p95 和 Subtask 分布使用 `Day4SkewBenchmark` 的本地显式探针：文章 `p95 9.79 -> 7.23 ms`，Subtask `480/11160/360 -> 5681/2426/3893`；IP `p95 3.69 -> 4.73 ms`，Subtask `11520/360/120 -> 3796/3759/4445`。Docker 证据用于后端资源和作业完整性对照，不能把两种环境的 p95 混成一张指标。

### 7.3 切换依据

当去重状态或 IP 集合接近可用 JVM 堆、Full GC/Checkpoint 已影响业务，或状态规模持续增长且合理 TTL 仍无法控制时，评估切换 RocksDB。切换前必须用同批数据证明结果一致，并确认 Docker TaskManager 有足够托管内存和本地磁盘；还要关注本次观察到的 Checkpoint 失败和 Docker 磁盘余量风险。RocksDB 不是因为“能承载大状态”就自动更快。
