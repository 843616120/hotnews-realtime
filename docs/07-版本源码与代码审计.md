# 07 版本源码与代码审计

## 概念说明

编译兼容、连接器能运行、Savepoint 可恢复、业务结果正确是四种不同的验证。Checkpoint/Savepoint 保存 Flink 状态和 Kafka 消费进度；MySQL/Redis 外部写入不属于同一事务。审计 AI 辅助编写的代码时，须从真实方法与已采集证据检查边界条件、状态及幂等，不能用注释或“作业 RUNNING”代替结果核对。

本次源码阅读路线：`FlinkSourceUtil.getKafkaSource`（group/起点） -> `ArticleJoinBehavior.etl` / `BehaviorDeduplicate` / `ArticleBehaviorJoin`（校验、状态、补关联和旁路） -> `RoleStreamUtil.restoreBehaviorTime` / `prepare`（时间戳、去重） -> `Achieve_roleAll` 的 A/B/C 分支 -> `FlinkSinkUtil.JdbcBatchSink` 和 `Achieve_roleB.REDIS_SCRIPT` -> `FlinkRuntimeUtil.configureCheckpointing`。进一步排查可从 Flink 1.17 的 `CheckpointCoordinator`、`StreamTask` 和 KafkaSource split/offset 恢复实现入手；这里是阅读路径，不宣称逐行审过 Flink 上游源码。

状态兼容边界：统一作业固定 8 个 Join 盐、Keyed State 描述符、keyBy 逻辑及算子拓扑。变更它们、序列化器或状态后端时，应先保存可用恢复点并单独验证；JDBC batch 等非状态参数变更不能据此推断状态结构变更也兼容。作业使用 `flink-runtime-web` provided 依赖供 IDEA 本地 MiniCluster 看 Web UI；统一入口仅本地配置 `10011`，Docker JobManager 使用 `8081`。

## 问题和结论

针对当前 AI 辅助实现，选三处真实风险进行代码审计：

1. **Checkpoint 与外部写入的原子性**。`FlinkSinkUtil.JdbcBatchSink.snapshotState()` 刷新 JDBC batch 后才确认快照；若快照失败并回退，先前提交可能重放。`clean_behavior` 按 `event_id`、A/B/C 按各自窗口业务键 UPSERT，Redis 脚本拒绝旧窗口/旧 revision；契约测试通过，但仍不能称 MySQL/Redis 与 Kafka 是跨系统事务 Exactly-Once。关注相同 revision 不同内容、旧文章版本等业务冲突的最终一致性。
2. **B 的串行窗口与写入同链**。`Achieve_roleB.buildRule` 使用 `windowAll`，统一作业 B Window 与 MySQL 榜单 Sink 同一 Vertex、并行度 1。Day6 某一阶段 busy=1000ms/s 且上游反压，但后期 B 闲置而热点 Reader 仍反压。Web UI 的忙碌值不能分离窗口计算与 JDBC 等待，也不能把所有阶段的瓶颈都归因于 MySQL。应对同一输入批次采集同一时段的各 Subtask、Kafka 位点和 CK 后再调整。
3. **Schema 描述、消费起点和输入批次可能被混淆**。`generator/schemas/*.json` 描述完整的干净事件约束，但 `ArticleJoinBehavior.validate` 是部分字段的运行时检查，并不执行 JSON Schema 的所有正则、长度/IP 格式约束。行为流优先从组提交位点消费，无位点则 earliest；文章流始终 earliest。旧消费组、旧 CK 和新生成批次/未清理结果表混用时，单靠数据库行数不能证明本批输入及全量正确性。核对需记录输入哈希、两流位点、消费组、Job ID、窗口闭合情况。

**结论**：当前版本组合在已记录的运行、Savepoint 非状态配置恢复、单 TM 再次故障恢复和 Sink 幂等契约范围内验证通过；统一作业的固定批次全量 B 结果与持续处理 >=2000/s 两项不能写为通过。以上结论基于项目源码和原始指标，不把其他批次/场景的通过结果外推。
