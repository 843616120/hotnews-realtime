# 08 Rule B 两阶段聚合与补算优化笔记

## 概念说明

单并行度 `windowAll` 会把全部分类窗口汇聚到一个子任务；下游写入慢时，还可能沿窗口、Join、Source 向上游传播反压。两阶段聚合先按分类和盐分散计数，再按十分钟窗口合并分片快照并生成全局 Top5。分片的累计快照必须按分片键替换，不能把迟到触发的累计值再次相加。Web UI 的 busy 表示算子忙碌，不等于反压；负载已结束时的 0 反压也不能证明高峰持续处理能力。

## 项目中的具体实现

- 统一作业 `Achieve_roleAll` 只 Join 一次，随后 A/B/C 共享清洗行为。本次 IDEA 作业使用 HashMap 状态后端；用户设置 Kafka `consumer_byte_rate=2.097152E7`。这是消费字节速率限制，不是经 Web UI 证实的每秒事件处理量。
- Rule B 保持事件时间十分钟滚动窗和 65 分钟允许迟到：第一阶段 `category + event_id hash` 的 8 盐聚合，并行度 3；第二阶段按窗口起点合并分片快照，并行度 2。局部保留文章计数到合并阶段，最后统一生成分类 Top5 和 `top_articles[]`，避免局部截断改变全局排名。
- A/B 窗口的合并触发器用一秒处理时间定时器减少频繁修订输出，但窗口归属仍使用事件时间。Rule B 的 MySQL `category_rank` Sink 按窗口起点和名次分区，并行度 2、独立算子链；Redis 仍保存 `hotnews:top5:latest` 完整榜单。没有添加中间 Kafka。
- `RuleReplaySink` 对已经超出在线等待范围的 A/B/C 窗口，在成功 Checkpoint 后从持久化的 `clean_behavior` 明细重新计算并 UPSERT；A 的部分过期滑窗也可触发补算。该机制依赖同批清洗明细完整落库，不能仅凭出现 late 旁路就认定补算已完成。

## 测试结果

### 2000 events/s 目标档

2026-10-08 本地 Web UI 作业 `1539ccc34d8172a24de69b955b33ecd5`，54 个子任务；文章 Source 并行度 3，行为 Source、Join 和 B 分片窗口并行度 3，B 排名合并与 MySQL 榜单 Sink 并行度 2。采样期间第一批行为 Source 累计读取约 100000 条。B 分片窗口三个子任务累计输入 `32114 / 32087 / 30882`，最大占比约 33.8%；合并窗口累计输入 `3383 / 2596`，MySQL 榜单 Sink 累计输入 `502 / 692`。窗口修订会多次写入同一主键，不能把 Sink 的累计输入当成最终榜单行数。

在 B 链路采样时，分片窗口、合并窗口和 MySQL Sink 的各子任务反压比率均为 0；Join 三个子任务反压比率约 `3.0% / 2.9% / 0%`，行为 Source 一度为 `0.3% / 29.0% / 6.2%` 的短暂低级反压，后续查询恢复为 0。故结论是 **B 旧版的持续单点反压未在本轮采样中复现**，并非整条链路运行全程没有反压。Join 各子任务的 ETL 到输出滚动 p95 分别为 `6344 / 4770 / 2978ms`，不是 Kafka 到 MySQL 的全局端到端 p95。Checkpoint 采样时 5 次成功、0 次失败，其中一次耗时约 31.9 秒；TaskManager 单点 Heap Used 约 1.03 GB / Max 3.27 GB，网络缓冲使用约 15.9 MB / 67.1 MB，不能将单次使用量视为内存峰值。

### 5000 events/s 目标档

继续在**同一 Job ID、同一状态**上运行生成器；采样时 B 分片窗口、合并窗口、MySQL Sink 和 Redis Sink 各子任务的反压比率均为 0。行为 Source 某一分钟滚动速率样本约为 `757 + 739 + 170 = 1666 records/s`；这是 Flink Source 当时的一分钟 Meter，不是生成器的目标发送速率，也不能推算稳态 5000/s。采样时 Checkpoint 累计 18 次成功、0 次失败。

这一档的行为 Source 累计读取数由第一批约 100000 增至约 300000，但 B 分片窗口累计输入仅由 `95083` 增至 `95988`，MySQL 榜单 Sink 累计输入由 `1194` 增至 `1239`。这些增量说明后续 Kafka 记录并没有作为等量的新清洗行为进入 B；同一作业保留去重状态，不能把 Source 累计数或生成器设定值直接当成 B 的有效输入。因此本档可以佐证采样期间 B 链路无反压，**不能单独证明 B 持续处理 5000 条有效行为/秒**，也不能把两档算成严格同位点、同状态的吞吐提升倍数。

### 固定输入结果一致性（与两档性能采样分开）

此前一次完成消费、等待补算结束后，使用同批固定输入、对应 Flink 日志、MySQL/Redis 只读快照执行 `verify.js` 全量逐字段核对：文章原始/清洗为 `500/500`，行为原始/清洗为 `100000/95082`，独立 SQL Join 为 `95082`。结果如下；这些 **PASS 属于那次固定输入核对**，不冒充上述复用状态的 2000/5000 档各自重新验收。

| 结果 | SQL 基准 | Flink 最终结果 | MySQL / Redis 快照 | 缺失 / 多出 / 字段差异 | 结论 |
| --- | ---: | ---: | ---: | --- | --- |
| Rule A `article_alert` | 123 | 123 | MySQL 123 | 0 / 0 / 0 | PASS |
| Rule B `category_rank` | 64 | 64 | MySQL 64 | 0 / 0 / 0 | PASS |
| Rule C `ip_alert` | 1 | 1 | MySQL 1 | 0 / 0 / 0 | PASS |
| Redis 最新 B 窗口榜单 | 4 | 对应最新窗口 | Redis 4 | 0 / 0 / 0 | PASS |

Redis 只保存最新窗口，不与 MySQL 的 64 条历史行比较；榜单按排名、分类、分数及 `top_articles[]` 核对。逐字段一致性证明本次拓扑改造没有改变该固定输入的最终结果，不等于证明高负载下的持续吞吐达标。

## 问题

旧版 B 的 `windowAll` 并行度为 1，曾采到约 `940ms/s` busy 且上游有明显反压；旧窗口与 JDBC Sink 同链，不能仅凭 busy 把责任全部归给窗口或数据库。新版将合并与 Sink 拆到两个子任务后，本轮未观察到 B 链路持续反压，但样本中包含读完批次后的空闲时段，缺少连续高负载的同口径前后吞吐曲线。5000 档复用前一档状态，Source 新读数据大量没有到达 B，不能以这一轮断言全链路稳定达到目标速率。

## 结论

本次改造解除了 Rule B 的单并行度聚合与单 Sink 限制；2000 和 5000 两档 Web UI 采样里 B 两级窗口及 MySQL Sink 均未见持续反压。单独固定输入的一次全量校验中 A/B/C、MySQL 和 Redis 最终结果逐字段一致。性能结论限于已观测时段和实际进入 B 的记录；要验证 5000 条有效行为/秒的稳态能力，须使用新的事件 ID 和独立消费组/状态，持续采集 Source、B 两级及 Sink 同时段吞吐、Kafka Lag 与端到端延迟。
