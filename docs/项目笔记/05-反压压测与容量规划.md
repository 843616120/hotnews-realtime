# 05 反压压测与容量规划

## 指标口径

反压由最慢的下游向上游传递；判定时联合 Source/算子/Sink 的 records in/out、busy/backpressured 时间、Kafka 消费组 Lag、Checkpoint 完成/失败/对齐时长，以及事件产生到结果可见的 p95。`rate` 是目标输入率，不是实际吞吐；短作业的总行数除以墙钟时间混入启动/结束成本；最后一条的延迟 Gauge 不是 p95。Lag 应用 Kafka `LOG-END-OFFSET - CURRENT-OFFSET` 逐分区求和，不能拿应用内 `emitted-consumed` 代理冒充。

## 项目试验与原始数据

[`Day6BackpressureJob`](../../flink-job/flink-rolesachieve/src/main/java/Day6BackpressureJob.java)是与业务 Topic/业务表隔离的规则 A 计算路径，可选内置限速 Source 或隔离 Kafka Topic；[`Day6DelaySink`](../../flink-job/flink-rolesachieve/src/main/java/Day6DelaySink.java)用每条 `Thread.sleep` 模拟 MySQL/Redis 变慢，**并不写真实数据库**。[运行器](../../tests/day6/run.ps1)控制速率、时长、延迟和 Sink 并行度；[原始 JSON](../../tests/day6/results/)通过 REST 记录任务、Checkpoint 与采样指标。

| 试验 | 可核对证据 | 解释 |
| --- | --- | --- |
| 隔离 Source 2000/5000 档 | `stable-2000-verified-...json`、`stable-5000-...json` | 两次采样期间各 5 次成功 Checkpoint、0 次失败；速率仍应按相邻计数样本计算，不直接填目标值 |
| 模拟慢 MySQL Sink，并行度 2 -> 4 | `slow-mysql-p2-...json`、`tuned-mysql-p4-...json` | 用同样延迟比较 Source 反压和 Sink 消费速率；不能推断真实 JDBC 批量写性能 |
| Kafka 慢 Sink | `kafka-slow-...json`、`kafka-slow-muw95ftn-run.json` | 40,000 条以约 1999.6 条/s 生产；结束采样的两个分区 Lag 为 4995 和 5993，合计 **10988**，另一分区为 0 |

| Day 4 倾斜 | [原始 HashMap/Docker 样本](../../tests/day4/evidence/) | 解释 `keyBy` 单热点与 16 分片；采集的生产作业 p95 字段为 null |

原始数据的逐档计算见[Day 6 现场报告](../05-反压压测与容量规划.md)：隔离基线 2000 档有效区间约 1999/s，5000 档约 4984/s；同样 50000 条输入下模拟 Sink 并行度 2 -> 4，作业完成时间从 54.667s 降为 28.343s。现场报告还记录 TaskManager 内存、状态增长档快照约 5.86 MB 和 Web UI 反压截图。这些试验已观察到隔离场景的反压和 Kafka 积压；尚不能证明完整 `Kafka -> Join -> A/B/C -> 真实 MySQL/Redis` 在 2000 events/s 下**稳定**且满足端到端 p95。部分样本的 `busyTimeMsPerSecond` 为 `NaN` 或前几秒为空，计算比较时只用有效 RUNNING 区间和明确的计数差。

## 容量、定位与调优

积压增长约为 `(生产速率 - 消费速率) × 秒数`；恢复追平时间约为 `待处理事件数 / (恢复处理速率 - 持续新流入速率)`，分母不大于 0 时**无法追平**。Kafka 保留时长要覆盖发现、止损、修复、重启和追平时间；应核对原始 Topic 实际 retention，不能仅凭公式保证。降低 Source 并行度只会限制读取速率，不能提高慢 Sink 的总处理能力。

定位次序：先看各分区 Lag 和 Source 读取，再看下游 Subtask 的 backpressured/busy 时间及 Key 分布；Sink 慢则核查写批、并行度、连接池和外部存储吞吐；状态增长则对照 JVM 堆、GC、托管内存、后端目录和 Checkpoint 字节/耗时；网络内存不足要排查 shuffle 缓冲与 Flink 报错，不能与 GC 或 OOM 混称。演练可以在隔离任务中缩小资源或增加高基数键，但不得把模拟状态增长描述为生产故障。真实主链路的 2000/5000 档、p95、截图和两阶段调优结果仍需补采。

**结论：**隔离探针证明了受控慢 Sink 会形成可观测积压，并记录了调大并行度与追赶方案；它是瓶颈定位证据，不是 MySQL/Redis 生产容量报告。
