# 第六天 2000 档：MySQL batch=1 的现场记录（进行中）

## 概念说明

生产者目标发送速率不等于 Flink 稳态消费能力。反压应同时看下游 busy、上游 backpressured、Kafka broker 末端与 Source 当前位点；Checkpoint 提交位点和正在读取的位点也不是同一口径。Join 的 ETL 到输出 p95 包括排队及等待，不是纯计算时间。

## 问题和结论

**现象**：Source/Join 接近满反压、Kafka 积压，#10/#11 Checkpoint 连续 180s 超时；单分钟 Source 约 12.52/s，未达到 2000/s。**证据**：上述 REST 原始目录中的 `job.json`、`metrics-*.json`、`backpressure-*.json`、`checkpoints.json`、`tm-metrics.json` 和 Kafka 位点 JSON。**定位**：B 单并行度窗口与 MySQL category rank Sink 同链满 busy；clean MySQL 链也明显反压。batch=1 是主动降速的候选原因，但无同输入/同配置的正常批量对照，不能断言唯一瓶颈。**处理/回归**：尚未进行；需要等待/安全停止本轮，恢复批量 100 或 200，重启同拓扑，用独立数据批次重复 2000/s，并逐点采集实际 producer 速率、Source/Sink 吞吐、Lag、CK 与 p95。不要一边积压一边追加 5000 档并把两轮混称独立结果。

按 14:44:48 的 60 秒 Source 约 12.52/s 作**条件估算**，无新消息且保持此速率时，72,340/12.52 约 5,778s（96 分钟）才能追平；这不是已实测的稳定服务能力或实际追平时间。若仍持续以 2000/s 写入，则积压理论增长约 1987.5/s；须用同期 broker 末端位点差分和 Source 位点差分验证，不能用这项算术估计替代实测。降低 Source 并行度只会限制消费、缓解内部压力，不会增大 B 窗口/JDBC 的总服务能力，还可能使积压更快增长。
