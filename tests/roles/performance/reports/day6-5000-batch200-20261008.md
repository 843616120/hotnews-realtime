# 第六天 5000 档：MySQL batch=200 运行记录

## 概念说明

生成器目标速率与 Flink 持续处理能力不同。要认定稳定 2000 events/s，必须在持续生产且结果链路有实际输出时测 Source、规则、Sink 的可持续吞吐，并检查 Lag/Checkpoint 是否不持续恶化。窗口的 5 行修订会使结果 Sink 的写入次数大于输入事件数，不能把 Sink 写入次数当业务事件吞吐。

## 项目中的具体实现

- 用户确认容器 MySQL batch=200，生成器目标 5000 events/s，并重新提交统一规则作业；`deploy/.env` 读取值为 `HOTNEWS_MYSQL_BATCH_SIZE=200`。没有保存容器 `printenv` 和生产者实际起止时刻/ACK，故目标速率不等于已验证的实发速率。
- Flink 1.17.0 新 Job `24f327b9643e65225dacc62a794b3cee`，并行度 3、42/42 RUNNING、1 TM/8 slots；Kafka broker `topic_behavior` 当前 6 个分区末端之和 100000，保留期 `retention.ms=604800000`。这一批次的位点分布不同于慢档，不把两批混成相同原始消息。
- 原始 REST 证据：`tests/roles/recovery/evidence/20261008-145959-816-day6-5000-first`、`20261008-150149-818-day6-5000-second`、`20261008-150309-239-day6-5000-third`、`20261008-150436-036-day6-5000-fourth`；Kafka broker 只读元数据 `tests/roles/performance/evidence/day6-5000-20261008/kafka-first.json`。
- 后续四轮原始 REST 证据：`tests/roles/recovery/evidence/20261008-150758-969-day6-5000-fifth`、`tests/roles/recovery/evidence/20261008-151057-833-day6-5000-sixth`、`tests/roles/recovery/evidence/20261008-151406-499-day6-5000-seventh`、`tests/roles/recovery/evidence/20261008-151727-350-day6-5000-eighth`。末轮验证本批次 Source 追平且下游采样空闲，不代表连续 5000/s 稳态能力。

## 问题和结论

**现象**：batch 200 后 CK 成功，但上游曾反压、Kafka 曾积压，最终读完固定的 100,000 条且末轮下游采样空闲。**证据**：以上八轮 REST 原始采集及 broker 末端位点；第六轮 Vertex 汇总值滞后，已用 Subtask 和位点交叉确认。**定位**：早期 B `windowAll` 与 MySQL 榜单 Sink 同链满 busy，下游 clean 链也被反压；后期 B 闲置而热 Kafka Reader 仍反压，说明瓶颈随阶段变化且分区倾斜明显。Redis Sink 不忙，未见网络内存或 GC 耗尽。只看同链 busy 尚不能把 B 的计算与 JDBC 各自耗时精确拆开。**处理**：MySQL 批量从慢档 1 恢复为 200；**回归**：本轮 CK #1~#18 成功、失败 0，Source 区间约 79/98/167/130 条/s，最后消费追平；两轮生产目标不同（2000/5000）、输入批次不同，不能计算 batch 参数的严格单因子提速倍率。

当前**未满足稳定处理 >=2000/s**；固定批次最终读完，不能代替持续生产时积压不增长的验收。降低 Source 并行度只会让入口更慢，B 的单并行度窗口+写入链不会因此提升总服务率。下一步需在停止/隔离当前作业后拆分 B 窗口计算与 JDBC 写入的耗时，评估两阶段聚合或减少重复修订写入，并在同速率同批次口径重新验收；不能在现有运行 Job 上热改有状态的 B 算子并假定旧 Savepoint 可恢复。实际 OOM/资源风险演练、截图、生成器 ACK 速率以及达到 2000/s 的稳态证明仍待完成。
